c-thru — routing Claude Code to the models you actually want

Why it exists, what it unlocks, and exactly how a prompt becomes a model call. Examples follow the shipped config/model-map.json, mode best-cloud, tier 64gb.

The problem

Claude Code is a genuinely good agentic harness. But the harness and the model underneath it arrive as one package — and there are real reasons to want a different model behind the same workflow.

Maybe the code cannot leave the building. Maybe you are burning frontier-model budget on work a cheap open-weights model would do just as well. Maybe a compliance rule rules out certain vendors, or you simply think one model plans better while another one writes better tests. Normally acting on any of that means patching the vendor CLI, or giving up the agentic workflow and driving raw APIs yourself.

Without c-thru

The model is a property of the tool. Changing it means changing — or forking — the tool. One backend goes down, the session goes down with it.

With c-thru

The model is a property of the config. The CLI is untouched, routing is a one-value edit, and a dead backend transparently becomes a live one.

c-thru is a local proxy plus a thin routing layer. Claude Code still runs unmodified; it just talks to 127.0.0.1 instead of straight to the vendor.

Key terms

Six words do most of the work from here on.

agent
A named worker you can hand a task to. Most name a job; five name a model.
capability
The role an agent resolves to, and what routing is actually keyed on. Usually the same word as the agent.
routing mode
Which family of models you want: frontier cloud, open-weights cloud, fully local, or origin-filtered. Five values.
hardware tier
Detected from your RAM — 16, 32, 48, 64 or 128 GB. Lets one config serve a laptop and a workstation.
endpoint
A configured backend: its URL, its auth, and the wire format it speaks.
wire format
The request shape a backend expects — Anthropic, Gemini, or OpenAI Responses. The proxy translates between them.

How it works

Which install you have matters from here on. Routing by agent name needs the hook and the agent fleet, and those ship with the CLI install. The marketplace plugin gives you the proxy and routing but not the fleet — so the mechanism below is a CLI-path feature.

You call an agent by name. A hook tags the request with that name. The proxy looks the name up, decides which model should serve it, and translates the call.

You rarely name an agent yourself. Each agent file carries a description — coder's begins “MUST BE USED for all code implementation tasks” — and the injected system prompt tells the main loop to read those descriptions and delegate before doing non-trivial work itself. So you type “implement the JWT middleware” and the main loop picks coder. You can also ask directly: “use the tester agent on this”, or, for the five that name a model, “ask agent grok to critique this plan”.

The trick is that most agent names describe a job, not a model. coder says what the work is; which model does it is decided at request time from the capability, the routing mode, and your hardware. Five agents — grok, gemini, kimi, deepseek, qwen — are the deliberate exception and name a model directly.

These are the defaults shipped in config/model-map.json, generated from that file and checked cell-by-cell against c-thru explain — 500 combinations, no disagreements. Your own ~/.claude/model-map.overrides.json can replace any cell, which is exactly the point: swapping a model is a config edit, and no agent file changes.

What you actually type

  

    Routing is a launch-time choice, so most of this is one flag. Nothing below changes any agent file.
  

  
# launch Claude Code through c-thru (cthru is an alias for c-thru)
cthru                              # the default mode
cthru --mode best-local-oss        # nothing leaves the machine
cthru --mode best-cloud-oss        # open-weights for the bulk work

# "why did it pick that?" — pure config lookup, no proxy, no request sent
c-thru explain --agent coder --mode best-cloud --tier 64gb

# active profile, routes, backend health
c-thru list

# edit the model-map, then reload a running session in place
c-thru reload

  

    Then, inside the session, you address the fleet in plain language — “ask agent grok to
    critique this plan” — or run /cplan "add JWT auth" to drive the full
    planner → coder → reviewer → tester wave.
