# Hardware Profile Matrix

c-thru resolves each agent to a concrete model through a 3-step chain: **agent name →
`agent_to_capability` → `llm_profiles[capability][mode][tier]`**. Hardware tier is
auto-detected at proxy startup via `tools/hw-profile.js:tierForGb()` and is one of
`16gb` / `32gb` / `48gb` / `64gb` / `128gb`. Mode is one of the 5 built-ins
(`best-cloud`, `best-cloud-oss`, `best-local-oss`, `best-cloud-gov`, `best-local-gov`)
or a declared custom mode — see [`docs/connectivity-modes.md`](connectivity-modes.md).
Each `llm_profiles[capability][mode]` entry also carries sibling `on_failure`
(`cascade`/`hard_fail`) and `fallback_to` keys — see
[`docs/model-map.md`](model-map.md).

> **This doc does not hand-maintain a capability × tier matrix.** It used to, and that
> table silently went stale after an agent-roster refactor — nobody noticed because
> nothing checked it against the shipped config. The canonical, always-current answer
> to "what model does agent X get at tier Y under mode Z" now lives in one place that
> can't drift silently: README's **[Agent routing reference](../README.md#agent-routing-reference)**,
> generated by `tools/gen-routing-doc.js`, checked on every commit
> (`gen-routing-doc.js --check`), and live-verified across all 5 modes × 5 tiers by
> `test/agent-mapping-complete.test.js`. If you're tempted to add a matrix back here
> instead of trusting/regenerating that table, don't — it will go stale again the same
> way.

For the full 22-agent roster and wave/dispatch lifecycle, see
[`docs/agent-architecture.md`](agent-architecture.md).

## Tier override

Verify the detected tier:
```sh
c-thru list
```

Override for testing (e.g. simulate a 48gb machine) — `CLAUDE_LLM_MEMORY_GB` must be a
positive integer:
```sh
CLAUDE_LLM_MEMORY_GB=48 c-thru list
```

## Resolution path

`model: coder` in an agent's frontmatter resolves as:

```
coder
  → agent_to_capability["coder"] = "coder"
  → llm_profiles["coder"]["best-cloud"]["128gb"] = "gemini-pro"
```

(Confirmed against the shipped `config/model-map.json`; check README's Agent routing
reference for the current value of any other agent/tier/mode combination.)

Swapping an agent to a different capability: one line in `agent_to_capability`.
Swapping a tier's backing model: one line in `llm_profiles[<capability>][<mode>][<tier>]`.
Agent files never need to change.
